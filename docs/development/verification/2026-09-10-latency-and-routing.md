# 2026-09-10 지연 보고와 출력 재개방 순서

계획 8번(진단 도구)의 지연 표시와 ARC-01의 남은 라우팅 IO 조율을 처리했습니다.

## 지연 보고

Inspect의 "지연"은 출력 장치가 보고하는 값이었고, Roomcut이 더하는 지연은 어디에도
없었습니다. 이제 엔진이 자기 지연을 상태 응답으로 보고하고, Inspect는 장치 지연과
따로 표시합니다.

보고하는 값은 **의도적으로 더한 지연**뿐입니다. 리미터 룩어헤드(2ms)와 리샘플러
그룹 지연을 더합니다. 링 점유량과 드라이버·장치 버퍼는 넣지 않았습니다. 측정하지 않은
왕복 지연을 합계처럼 보여주지 않기 위해서입니다. EQ·공간계는 IIR이라 그룹 지연이
주파수마다 다르므로 단일 숫자에 포함하지 않았습니다.

`ctest -R latency` 4개 검사가 보고값을 실제 임펄스 위치와 대조합니다.

| 검사 | 결과 |
|---|---|
| 체인 임펄스 | 44.1/48/96/192kHz에서 보고값과 출력 피크 위치가 정확히 일치 |
| 비교 경로 | 체인 두 개를 돌려도 지연은 한 개일 때와 같음 |
| 리샘플러 임펄스 | 48→96k, 96→48k, 44.1→48k에서 보고값과 피크 위치 차이 1샘플 이내 |
| 동일 레이트 | 변환이 없으면 보고 지연 0 |

와이어에서는 `engineLatencyMs`를 상태 응답 끝에 덧붙였습니다. 이전 엔진의 짧은 응답은
그대로 파싱되고 값은 0(보고 안 함)이 됩니다. `test_control`이 실제 Mach 왕복으로
2.75ms를 주고받는 것을 확인합니다.

비교 준비 상태 문구도 함께 봤습니다. 현재 A/B 도움말은 측정 중·신호 부족·우회 중·
사용 불가를 각각 구분해 표시하며, 사실과 어긋나는 표현은 없었습니다. UI에 "헤드룸"을
주장하는 문구는 없습니다. 이번에 새로 만들지도 않았습니다.

## 출력 재개방 순서

`recoverOutput`은 main의 람다였습니다. 판단·정지·해제·개방·시작·감시자·볼륨 대상·
저장 장치·수명 전이를 한 자리에서 처리했고, 정책(`OutputRecovery`)만 검사가 있었습니다.
순서 자체는 검사가 없어서, 장치를 닫고 무언가를 되돌리지 않는 실수는 실기기에서만
드러났을 것입니다.

`OutputRouter`가 순서와 재시도 타이머, 렌더 폭주 감시를 소유하고 HAL 호출은 인자로
받습니다. `ctest -R output_router` 6개 검사입니다.

- 링이 없으면 장치를 건드리지 않고 재시도 타이머도 지웁니다.
- 대상이 바뀌면 `lost → stop → unwatch → close → open → start → restored` 순서로 진행합니다.
- 개방 실패나 시작 실패는 복구 단계를 건너뛰고 닫은 뒤 재시도를 예약합니다.
- 폭주 강제 재개방은 같은 장치를 다시 만듭니다.
- 드라이버의 첫 인계(`adopt`)는 예약된 재시도를 취소합니다.

동작은 그대로입니다. 같은 순서, 같은 로그, 같은 수명 전이입니다.
