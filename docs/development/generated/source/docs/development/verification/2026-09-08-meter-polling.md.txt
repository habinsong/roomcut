# 2026-09-08 장치 읽기와 미터 갱신 분리

UI 구성과 미터의 기존 표시 규칙은 유지했습니다. 비동기 장치 조회를 기다리는 동안 폴링 전체가 멈추는
의존 관계를 제거했습니다.

## 재현과 변경

장치 읽기를 보류한 뒤 피크를 0.8로 바꾸고 실제 폴링 타이머를 250ms 진행시켰습니다.
기존 코드는 상태 조회가 1회에 머물고 미터가 0이어서 두 검증 항목이 실패했습니다.
수정 후 같은 조건에서 상태 조회는 3~4회, 실제 장치 읽기는 1회였고 피크 0.8이 반영됐습니다.
이 수치는 테스트 클라이언트의 관찰값이며 실기기 프레임 속도 측정은 아닙니다.

| 파일 | 책임 |
|---|---|
| `DeviceReadCoordinator.swift` | 장치 읽기 한 건과 최신 대체 요청 한 건, 결과 대기·취소·컨텍스트 검증 |
| `EnginePoller.swift` | 빠른 상태 주기의 수명과 장치 읽기 완료 시점 기록을 구분 |
| `RoomcutViewModel.swift` | 타이머는 장치 읽기 완료를 기다리지 않으며, 현재 장치/리비전의 결과만 게시 |
| `DeviceReadCoordinatorTests.swift`, `PollingLifecycleTests.swift` | 공유·교체·취소·재시작·연결 끊김·미터 진행 회귀 |
| `Package.swift` | 새 읽기 담당을 RoomcutCore에 연결 |

같은 요청은 진행 중 읽기에 합류합니다. 장치/리비전이 바뀌면 이전 결과는 버리고 최신 대체 요청만 남깁니다.
추가로 필요한 목록/컨트롤 정보는 대체 요청 하나에 합칩니다. 중단해도 실제 호출이 끝나기 전에는 진행 슬롯을 비우지 않습니다.

명시적으로 호출한 `refreshNow()`는 요청한 장치 정보 완료를 기다릴 수 있지만, 타이머와 쓰기 후 상태 확인은
빠른 상태 주기만 기다립니다. 새 상태 조회는 이전 장치 읽기가 끝나지 않아도 진행됩니다.
연결 끊김과 폴링 중단은 보류된 결과를 무효화합니다.

완료 대기는 작은 Ticket으로 공유하며, 모든 가변 필드는 NSLock으로 보호합니다.
취소 핸들러가 메인 액터 밖에서 실행될 수 있어 이 타입에만 `@unchecked Sendable`을 사용했습니다.
계속된 읽기를 강제로 중단하는 것이 아니라 결과 전달과 기다리는 호출을 종료합니다. 공유 요청이 취소되면 그 요청의 대기자도 함께 종료됩니다.

| 평가용 앱 | Home·Inspect 전환과 미터·장치 표시 확인 | [UI 관찰](raw/2026-09-08-meter-polling/ui-smoke.txt) |

검증한 경계:

- 같은 읽기를 100회 요청해도 네이티브 읽기를 추가하지 않습니다.
- A가 읽히는 동안 B·C를 요청하면 B는 실행하지 않고 A 다음 C만 실행합니다.
- 중단 후 새 요청을 시작해도 이전 네이티브 읽기와 겹치지 않습니다.
- 추가 요청한 목록·컨트롤 부분은 한 번의 후속 조회로 합칩니다.
- 취소된 여러 대기자는 종료되며, 뒤늦은 네이티브 완료를 다시 전달하지 않습니다.
- 연결이 끊긴 뒤 오래된 값으로 장치/볼륨을 복원하지 않습니다.
- 장치 전환 뒤 이전 장치의 볼륨이 잠깐이라도 게시되지 않고 새 장치 값만 적용됩니다.
- 기존 편집 이름·A/B·미터의 독립 게시 검사는 유지했습니다.

## 중단했던 검사

초기 대상 검사에서 `testVolumeEditOutlivesAnOlderDeviceReadback`이 대기 상태에 머물렀습니다.
실행 중인 XCTest를 확인하고 스택을 채집한 뒤 해당 테스트 프로세스만 종료했습니다.
출력에서 앞선 검사들은 통과했고 이 검사에서 대기했음을 확인했습니다.
새 구조는 이전 완료 직후 대체 읽기를 시작하는데, 테스트 클라이언트가 모든 후속 읽기까지 보류하고 있었습니다.
의도한 한 번의 읽기만 보류하도록 테스트 입력을 수정한 뒤 전체 검사를 다시 실행했습니다.
실패/대기 기록을 삭제하거나 테스트를 제외하지 않았습니다.
[중단 기록](raw/2026-09-08-meter-polling/targeted-interrupted.txt), [프로세스 스택](raw/2026-09-08-meter-polling/hung-test.sample.txt).

## 참고와 한계

[Swift 동시성 제안서](https://raw.githubusercontent.com/swiftlang/swift-evolution/main/proposals/0304-structured-concurrency.md)와
[Apple 응답성 지침](https://developer.apple.com/documentation/xcode/improving-app-responsiveness)을 확인했습니다.
비동기 호출이 UI 스레드를 막지 않는 것과 독립적인 폴링 진행을 구분했습니다.

평가용 앱은 메모리 fixture이며 실제 장치 지연·재생·청취를 검증한 것은 아닙니다.
실제 엔진 상태 응답 자체나 다른 RPC가 느린 경우까지 일정한 미터 주기를 보장하지 않습니다.
이미 적용한 결과를 취소가 되돌리는 것도 아닙니다. 네이티브 C/C++ 코드는 수정하지 않아 ctest는 반복하지 않았습니다.
다음은 IO-01의 복합 네이티브 쓰기 부분 실패 검증입니다. 전체 목표는 계속 활성 상태입니다.
