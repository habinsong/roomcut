# 지속 개발 이어가기

이 파일은 컨텍스트 압축 뒤 현재 작업을 복구하는 시작점입니다. 기록보다 현재 파일·실행 중인 도구 상태가 우선입니다.
전체 목표는 기존 UI/UX 보존, 전체 구현 원문·계획 최신화, 결함 해결, 책임 분리, 레퍼런스 기반 기능, 품질/성능 개선과 실제 검증이며 끝나지 않았습니다.

## 다시 시작할 때

1. 이 파일, [현재 이슈](issues/current.md), [계획의 다음 시작점](plan/roadmap.md#다음-시작점), 가장 최근 검증 기록을 읽습니다.
2. `git status --short`와 대상 파일을 확인합니다. 기존 미커밋 작업을 보존하고 다른 작업의 변경을 되돌리지 않습니다.
3. 기록된 검사 핸들이 실제로 살아 있는지 확인합니다. 관찰 시간 초과만으로 같은 검사를 다시 시작하지 않습니다.
4. 재현·수정·검증을 마칠 때마다 이 문서와 이슈/계획/검증 기록, 전체 원문 생성기를 갱신합니다.
5. 전체 제품 목표를 한 번의 검사 통과나 작업 단위 완료로 축소하지 않습니다. 명시적 지시 없는 커밋·배포·실기기 설정 변경은 하지 않습니다.

현재 요청 범위는 다국어 문서, `1.0.9` 빌드 산출물, 커밋·푸시·GitHub 릴리스입니다.

### 현재 구현/증거

- 앱·드라이버·CMake 버전은 `1.0.9`입니다. 네이티브 CTest 37/37, Swift XCTest 213/213,
  앱 번들 서명 구조, `.pkg`·`.dmg` 생성과 이미지 체크섬을 로컬에서 확인했습니다.
  이미지 내부 `.pkg`와 독립 `.pkg`의 SHA-256도 일치합니다. 값과 범위는 2026-09-09 기록에 있습니다.
- 이 확인은 새 엔진을 실제 장치에 설치하거나 다른 Mac에서 업그레이드한 검사가 아닙니다.
  Developer ID 서명·공증도 수행하지 않았습니다.
- `BypassWriter` 86행, `BypassOverride` 37행이 직접 선택과 임시 측정 복구의 순서/소유권을 담당합니다. 뷰 모델에는 로직을 누적하지 않고 구성요소를 연결했습니다.
- 재현은 2개 테스트·4개 항목 실패, `[true, true, false]`의 오래된 복구가 최종 false를 만드는 경로였습니다. 수정 후 `[true, true]`, 최종 true입니다.
- 바이패스 대상 10개, 전체 Swift 211개, 관련 TSan 29개 통과. 자료는 `build/bypass-ownership-audit/`와 최근 검증 문서에 있습니다.
- 평가용 상태의 바이패스 readback 오류를 고쳤고 이전 단순 ON 관찰의 한계를 문서에 정정했습니다. `ui-roomtune`은 이제 5초 지연 응답과 평가 모드 전용 요청/적용 로그를 사용합니다.
- 첫 3초 UI 시도는 상태가 바뀐 뒤 클릭해 실제로 false를 요청했음을 로그로 확인했습니다. 5초 조건에서는 true 요청이 첫 응답보다 먼저 들어갔고 오래된 false 복구 없이 UI Off가 유지됐습니다. 정상 측정의 true→false 복구와 UI On도 확인했습니다.
- `AppLaunch.swift`는 실행 모드를 분리합니다. `--attach-engine`은 실제 엔진에 접속하고 창을 열지만 서비스 시작/재시도/종료는 수행하지 않습니다. 일반 실행은 기존 동작을 유지합니다.
- 실제 앱을 `com.roomcut.sound-qa` 복사본으로 빌드/실행했습니다. 시스템 기본 출력 Roomcut Output, 실제 iFi USB Audio SE, 384kHz·24-bit, 볼륨 0.063488125801086426을 확인했습니다.
- 6초 1kHz peak 0.01 검사음을 처리 켬/우회에서 각각 재생했습니다. 엔진 피크는 0.007373(-42.647dBFS)/0.01(-40dBFS), 신호 구간 언더런 증가 0입니다. 아날로그 녹음이나 주관적 청취 평가는 아닙니다.
- 실제 앱 UI로 바이패스를 원래 false로 복구했습니다. EQ/PEQ/볼륨/포맷/기본 출력은 검사 전과 동일하고 paramsRevision=7, keepDefault=true를 유지했습니다. 앱 종료 후 설치 엔진 PID 717도 유지됐습니다.
- 설치 엔진 바이너리는 `/Library/Application Support/Roomcut/bin/RoomcutAudioEngine`이며 작업 트리의 `build/engine/RoomcutAudioEngine`과 해시가 다릅니다. 실제 측정 결과를 새 엔진 실기기 검증으로 확대하지 않습니다.
- 두 QA 앱은 종료됐습니다. 닫힌 앱에 getApp/getAXState를 호출하면 무인자로 재실행될 수 있으므로 앱 목록으로 확인하고, 새 검사에는 정확한 실행 인자를 지정합니다.
- 마지막 재검사에서 `testFailedWriteRestoresEngineParams`의 고정 40ms 대기 문제가 드러났습니다. 80ms 지연으로 재현하고 실제 쓰기/복구 완료를 기다리도록 검사만 수정했습니다. 실패/수정 후 로그는 `build/sound-check-audit/restore-wait-*.log`입니다.
- 최종 전체 Swift 211/211 통과: `build/sound-check-audit/swift-tests-final.log`, 세션 2601 종료값 0 확인. 실행 중인 검사 핸들과 QA 앱은 없습니다.
- 최신 앱/서명과 실제 오디오 설정 원상복구를 확인했습니다. 전체 원문·해시·링크 일치 검사를 마지막에 갱신합니다.

### 재개 요청이 있을 때의 후속 작업

1. 이 문서·최근 검증 기록·현재 소스를 다시 확인합니다. 끝난 검사나 닫힌 QA 앱을 실행 중으로 간주하지 않습니다.
2. RT-05, ARC-01, ARC-02, ARC-03(일부), PERF-01, EQ-01, 계획 8번이 끝났습니다. 호스트에서 남은 계획 항목은 없고, 다음은 실기기 검증(HW-01·RT-01·계획 10번)과 Now Playing 보조 프로세스 수명입니다.
3. 실제 앱 QA도 계속합니다. 현재 출력/설정/PID를 먼저 읽고 필요 변경 후 복구를 확인합니다. 저장소의 `sudo` 금지는 유지하며 `--attach-engine`으로 기존 서비스를 관리하지 않고 접속할 수 있습니다.
4. 실제 마이크/권한/중단, 설치·새 엔진 바이너리 검증, 장시간/재연결/절전, 전체 주파수 응답/지연과 청취/녹음 근거는 별도로 남아 있습니다.
5. 원래 목표의 엔진/Now Playing 책임 분리, 선택적 다이내믹 EQ와 고샘플레이트 품질/속도 개선을 계속 진행합니다.
